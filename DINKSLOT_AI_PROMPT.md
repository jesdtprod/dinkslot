## 1. Product in one paragraph

Pickleball clubs and court owners (tenants) register on DINKSLOT. After the platform admin approves a club, it appears on the public landing page with its own club page. The club sets up its profile (cover photo and profile photo), courts, and a payment QR. Players join a club, pick a court and time slot, pay by scanning the club's QR outside the app, and upload proof of payment. The club admin verifies the proof and approves or rejects the booking. Players are notified by in-app notification and by email.

**v1 scope is booking and booking approval only.** Do not build tournaments, rankings, open play, subscriptions or online payments.

## 2. Hard rule: tenant isolation (highest priority)

**Club 1 must never be able to see, change or guess anything that belongs to Club 2.** This applies to every table, view, function, storage file, email and notification.

Enforce it in Postgres, never only in the frontend:

1. Every tenant-owned table has a `tenant_id` column (NOT NULL, foreign key to `tenants`).
2. Row Level Security is **enabled and forced** on every table. No table is readable or writable without a policy.
3. A club admin can access a row only if they have an active row in `tenant_members` for that row's `tenant_id`.
4. A player can read a row only if it is their own (`player_id` matches them) or it is public data of an approved club.
5. Players of one club are invisible to other clubs. A club admin sees only `club_players` rows for their own club.
6. Public pages read through views or functions that expose only approved clubs, active courts and non-sensitive fields.
7. `court_availability` returns only `court_id`, `starts_at` and `ends_at`. It never returns player names, ids, proofs or amounts.
8. Storage policies mirror table rules: files live under `<tenant_id>/...`, and a policy checks the first path segment against the user's club membership. Payment proofs are private to the uploading player and that club's admins.
9. Never pass `tenant_id` from the client and trust it. Derive it from the court, booking or membership on the server.
10. Every security-definer function must check `auth.uid()` and the caller's role first, and set `search_path` explicitly.
11. Soft-deleted rows (`deleted_at is not null`) are excluded by every policy and view.
12. The service role key is used only inside Edge Functions and is never in the repo or the browser.

**Isolation test (required before moving past Stage 2):** create two clubs, two club admins and two players. Using SQL run as each user (`set local role authenticated` with that user's JWT claims), prove that:

- Admin 1 cannot select, update or delete any row of club 2 in any table.
- Admin 1 cannot call `decide_booking` on a club 2 booking.
- Player 1 cannot read player 2's bookings, proofs or notifications.
- Admin 1 cannot read club 2's proofs or QR files through storage.
- An anonymous visitor sees only approved clubs and active courts.

Show me the terminal output of each check.

## 4. Database rules (apply to every table)

- **ULID primary keys**, stored as 26-character text, generated by a SQL function `gen_ulid()`.
- **Soft delete:** every table has `deleted_at timestamptz`. Never hard-delete business rows.
- **Timestamps:** `created_at` and `updated_at` on every table, with an update trigger.
- **Idempotency:** every write that a client might retry (creating a booking, uploading proof, deciding a booking) accepts an `idempotency_key`. A unique index makes a retry return the original result instead of creating a duplicate.
- All times are stored as `timestamptz`. The default club timezone is `Asia/Manila`.
- Keep the design general and reusable across my other projects. No hard-coded club names.

## 5. Booking rules

The database decides whether a booking is allowed. The frontend only calls functions.

**No double booking.** Use a Postgres exclusion constraint:

```sql
create extension if not exists btree_gist;

alter table bookings add constraint bookings_no_overlap
  exclude using gist (
    court_id with =,
    tstzrange(starts_at, ends_at) with &&
  ) where (status in ('pending', 'approved') and deleted_at is null);
```

**`create_booking(court_id, starts_at, ends_at, idempotency_key)`** checks on the server that:

- the caller is a signed-in player who joined this club and is not blocked,
- the club is approved and the court is active,
- the time is on the court's slot grid and inside its opening hours,
- the booking is within `booking_window_days`, `min_hours` and `max_hours`,
- no `court_blocks` row overlaps,
- the amount is computed from the court's `hourly_rate` (never trust a price from the client).

It creates a `pending` booking with a `reference_code`. If payment is on, it sets `expires_at = now() + pending_hold_minutes`.

**Pending hold:** `pg_cron` runs every minute and marks unpaid pending bookings past `expires_at` as `expired`. Once proof is uploaded, the hold stops expiring until the admin decides.

**`decide_booking(booking_id, decision, reason)`:** only that club's owner or staff. Only `pending` bookings. When payment is on, approval requires uploaded proof. Rejection requires a reason. Writes `decided_by`, `decided_at`, an `audit_log` row, a notification and triggers the email.

**`cancel_booking`:** a player can cancel until `cancel_cutoff_hours` before the start. A club admin can cancel any booking with a reason.

**States:** `pending` and `approved` hold the slot. `rejected`, `cancelled` and `expired` release it and are final. If a club turns approval off, bookings go straight to `approved` (after proof when payment is on).

## 6. Payments (manual QR)

- The club uploads one QR image (GCash, Maya or bank) and payment instructions. A court may have its own `qr_path`, which replaces the club's QR for that court.
- The booking screen shows the amount, the QR (the court's if set, otherwise the club's), the instructions and the `reference_code`.
- The player pays outside the app, then uploads a screenshot and types the payer reference number.
- The booking appears in the admin's approval queue with the proof beside it.
- Proofs accept JPG, PNG and WebP up to a size cap, enforced by a storage policy.
- The same payer reference cannot be used on two bookings in one club.
- A club can turn payment off in settings. Then the QR step is skipped.

## 7. Notifications

- **In-app:** `notifications` table plus Supabase Realtime (admin queue badge, player bell).
- **Email:** a Database Webhook on `bookings` calls the Edge Function `send-booking-email`. The browser never calls it. The function re-reads the booking, builds the email from a template, exchanges the stored refresh token for an access token, sends through the Gmail API over HTTPS, and writes `email_log`.
- Idempotency key for email: `booking_id:status`, so a replayed webhook never sends twice.
- Secrets: `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`, `GMAIL_SENDER`.
- Emails: booking received (player), new booking request (club admin), approved, rejected with reason, cancelled, expired.
- Display name is the club's name; `Reply-To` is the club's email.
- Design the send step so it can later be swapped for Resend without changing the webhook, templates or `email_log`.
